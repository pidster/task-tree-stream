# D01 / D09 paired adversarial review — 2026-09-14

**Reviewer:** reviewer agent (T1). **Status:** findings recorded; both docs moved to In Review. Nothing approved — a human approves.
Full findings are in each document's Review log. Counts: D01 5 blockers, 15 major, 5 minor. D09 5 blockers, 17 major, 5 minor.

## Top blockers

1. **Snapshot isolation does not give D01 or D09 what they assume.** The verified transactions note shows write conflicts are detected only on the *same record*. D01's cycle prevention (§3.4, D-3, TK-3) and gapless per-subject `seq` (TR-2), and D09's per-org audit `seq` and hash chain (§4.1, §4.3), all need an explicit serialisation point that neither doc has. Concurrent writes produce cycles, duplicate `seq`, and a silently forked audit chain.
2. **§4.2's one-transaction Transition-plus-audit-event rule makes the org-wide chain head a single-writer bottleneck** on every domain write — against O6 and D09's own T3.
3. **Identity is modelled twice and incompatibly**, and D01's `kind = system` principal (on which O8's never-null actor depends) is illegal under D09's invariants. The glossary has already committed to `Account`, which escalation E-03 has not decided.
4. **D09's permission model cannot express D01's domain**: no plan verbs at all (O3's premise), no way to enforce D01's human-only transitions, a `task.archive` verb for an operation D01 does not define, and no verb gating Dependency creation.
5. **Sensitive metadata is protected only in the audit event; D01's immutable `Transition.changed_fields` still copies the secret.**

## Recommended reconciliation of the D01/D09 overlaps

- **Identity entities:** D09 owns Organisation, Team, User, Membership, Grant and (if it survives) Account, with one field set. D01 keeps only `ref<Organisation>`, `ref<Team>`, `ref<User>` and the fact that every entity is org-scoped. D01 deletes its §2.1–2.3 field tables. Settles OQ-3.
- **System principal:** add `kind = system` to D09, exempt from I1's Membership rule and I3's owner rule, one per org, created with the org. D01 U-2 then stands unchanged.
- **Transition vs audit event:** keep both, but make Transition authoritative for domain state and the audit event a *derived security projection* written asynchronously, per project rather than per org. That removes the bottleneck and the fork, and stops the 400-day audit retention from outliving the record it claims to complete. Drop the hash chain to the hardening phase (OQ-8).
- **Agent ownership and decision rights:** D09 owns `User.owner`, agent `scope`, and `kind` gates. D01 owns `Escalation.requires_human` and `Decision.decided_by_kind`/`on_behalf_of` as fields, D09 owns the rule that only a non-delegated human may satisfy `requires_human`. Drop `allowed_with_human_review` — it is unrepresentable in D01's Decision model and no objective needs it.
- **Cross-project dependencies:** D01 must model the opaque blocker (an unreadable prerequisite with existence, direction and satisfied/unsatisfied only) and say what the stream's topological layer does with a prerequisite outside the plan. Without that, D09 §3.6 has nothing to attach to.
- **Sensitive metadata:** apply the sensitivity rule to `Transition.changed_fields` *and* the audit event, put the per-org declaration in a named place, and state explicitly that values logged before a key was declared sensitive are not recoverable.
- **Idempotency:** one mechanism, one name, one owner (D03), with the parameter-matching rule D01 specifies. Delete D09 §4.5's divergent 24-hour `(principal, key)` variant.

## Positions on the five open escalations (recommendations only)

- **E-01 cross-project dependency:** agree with option 2 (same org, authorisation-checked, org setting defaulting to same-project). But it is not decidable until D01 models the opaque blocker and the out-of-scope prerequisite in the stream. Decide the policy now, block approval of both docs until D01 carries the model.
- **E-02 sensitive metadata:** agree with option 3 and with per-organisation declaration. Both current positions are incomplete: they cover the audit event and miss D01's Transition. Reject option 4 explicitly, as proposed.
- **E-03 `Account`:** recommend **option 2** (no Account in v1), against both current positions. A6 rules out self-service signup, the deployment is self-hosted, and a human in two organisations is rare enough in v1 that two logins is an acceptable cost. Adding Account later is a credential migration for a small number of humans, not the whole estate. If the founder prefers option 1, the glossary is already consistent; if option 2, several glossary rows and D09 §2.3 must change in the same edit.
- **E-04 erasure versus immutability:** agree with option 1 for v1 (redaction only, deployer as controller), with the caveat that §4.3's redaction currently breaks the hash chain. If the chain is deferred as recommended above, this escalation becomes considerably simpler.
- **E-05 Rust as sole enforcement point:** agree with option 1 for v1, plus the mandatory D10 cross-tenant suite. Add two conditions: pin 3.2.3 rather than a 3.2.0 floor, since 3.2.0 is a version no project research has exercised; and record the "no custom API routes" constraint in D02 and D08, where it is currently stated only in D09.
